### Suggestions (2)

- **[types]** `server/src/routes/github-webhook.ts:818` and `:3411` — `reviewHasActionableFeedback` is now fully redundant with `reviewActionability.actionable`: it is written at exactly one site (`:1325`, immediately beside `reviewActionability` at `:1326`) and read at exactly one site (`:3411`). Keeping two fields that must agree reintroduces in miniature the drift class this PR exists to eliminate — nothing structural stops a future edit from setting one without the other. The consequence is specifically the invariant your own test asserts: if they ever disagreed with the boolean reading `true`, `isActionableReviewFeedbackContext` would return `true` from the stale field while `resolveReviewFeedbackSuppression` recomputed non-actionable, and `:5386` would write `githubReviewFeedbackActionable: true` **and** the suppression pair into the same `contextSnapshot` — the "cannot both be read as true" property, broken. Replacing `:3411` with `context.reviewActionability?.actionable` (falling through to the existing recompute when absent) and dropping the field makes the exclusivity structural rather than conventional. Unreachable today, since `resolveEventContextRaw` is the sole producer and sets both.

- **[correctness]** `server/src/routes/github-webhook.ts:3446-3448` — the recompute fallback classifies `context.reviewBody`, which is the **clamped** body (`:898-901`), whereas the primary path classifies `rawReviewBody` (`:1312`). On a clamped input the `all_zero` / `unenumerable` split is not sound: if the clamp lands *between* two bucket headings — `### Critical Issues (0)` surviving at, say, byte 4090 while `### Important Issues (1)` is cut at 4115 — then `extractAllyReportedFindingRefs` returns non-null-but-empty and the classifier reports `ally_review_findings_all_zero`, the *healthy* reason, for a body that was truncated with findings lost. That is exactly the confusion BLO-30420 exists to remove, reappearing on the fallback path. The 25-byte gap in the frr#61 specimen (4248/4273) shows how narrow the window is. It is unreachable in production for the reason above, and its only exercise is the synthetic literal in the `review_body_absent` test — so the cheapest fix is to drop the fallback (`if (!context.reviewActionability) return null`) and adjust that one test, rather than keep a path that can emit a confidently wrong reason. If it is kept deliberately, the comment at `:3428-3431` is worth extending to say the fallback reads a clamped body and its Ally-specific reasons are therefore lower-confidence than the primary path's.

- Acting on the type-narrowing suggestion is what turns the taxonomy from documented into enforced. `Extract<…, { actionable: false }>` is the right construction because it tracks the union automatically — a sixth reason added to the classifier propagates here with no edit, and a typo in a hand-built decision fails to compile.
